# 候选池状态优先的展示排序

这次重构把候选池从板块综合质量排序改为状态分组，再在同一状态内按个股证据排序。`score` 不再被换算成技术分或综合分，结构、相对强度、市场风险、真实技术快照和复评进度被单独持久化并展示；板块分数仅作为最后的平手裁决。多策略同代码在内部仍按“代码 + 策略”保存，界面则选择一条优先路线并合并显示路线标签。风险状态、封板和缩量已能从 BUY/NEAR/OBSERVING 分组中抽到第四档，但旧候选的市场风险快照和行情快照没有被当作准入新鲜度门槛。  

Watch for: **confirmed，高风险：**旧缓存或本轮没有市场风险快照的 `BUY_CANDIDATE` 仍会显示在“可参与候选”；**confirmed，中风险：**UI 会把恢复的非当日行情当作实时开板证据，清除封板/缩量暂缓标记；**confirmed，中风险：**文档承诺按“最近复评时间”排序，但模型只保存复评日期，无法在同日完成该排序。

**Verdict**: NEEDS_CHANGES

## High-level view

状态是展示的硬边界。`displayTier` 先把 `BLOCKED` 市场风险、突破风险、封板和缩量放到第四档，`prioritizedSections` 也对 BUY、NEAR、OBSERVING 三档重新分流，因此板块强度、资格命中数和技术快照都不能把已识别风险抬回可参与区。

同档排序器的证据顺序符合目标：结构优先于相对强度，再到市场风险、技术快照和复评信息，板块角色与板块强度位于代码稳定排序之前。旧记录的市场风险为 `null` 时仍是第一档；从落盘行情恢复的旧报价还会参与封板判断并临时移除风险标记。

每股单行的路线选择保留非封板路线优先，避免一条封板持续路线覆盖同代码的有效启动路线。界面也不再为候选池展示“综合质量分”。不过，复评时间没有在每一次复评后持久化，且现有测试没有执行排序器的优先级矩阵或 UI 的实际排序，无法保护这组核心承诺。

## 已确认的关键正确点

状态逆转已被阻断。风险标记的 BUY 候选会在 `prioritizedSections` 中转入第四档，`BLOCKED` 的持久化市场风险也已覆盖，修复了上一轮审查指出的 BUY 绕过问题。

同档排序没有回退使用 0–3 的资格 `score`。候选池行只显示结构、相对强度、市场风险和真实技术快照；技术快照缺失会明确标为“技术快照暂缺”，而不是伪造成技术分。

板块只在所有候选自身证据和复评信息相等后参与 `compareBoardTieBreak`。多策略候选先选择非封板路线，再按同一排序器选代表路线，界面把该股票的全部路线列在详情中。

## 旧候选缺少市场风险快照仍会进入可参与区

**confirmed，高风险。** 新字段在 `ObservationPoolJson.decode` 中对旧记录保留为 `marketRisk = null`，模型注释也把该值定义为“旧数据为空代表暂缺”。`ObservationEligibility.isRiskOrDeferredObservation` 只把 `marketRisk == BLOCKED` 识别为第四档风险；`null` 不会触发任何分流。于是一个旧的 `BUY_CANDIDATE` 即使没有本轮市场风险、相对强度或技术快照，仍由 `displayTier` 返回第一档，并被 `prioritizedSections` 放进“可参与候选”。

候选池规则把“数据不足”列为第四档，并要求等待风险解除或重建结构。规则另行允许缺少**技术快照**的候选留在同档末尾，这不等于允许缺少当日市场风险和行情门控的旧 BUY 继续作为可参与对象。应把技术快照缺失与交易风险输入缺失区分开：前者保留当前的末位展示；后者必须降为第四档，或至少显示为非可参与的过期状态，直到 `MonitorService` 以当日行情完成复评。

## 缓存行情会撤销封板和缩量暂缓

**confirmed，中风险。** `MonitorService.restoreQuoteCache` 在进程重启时把最近一次落盘行情写入 `Repo.quotes`，缓存设计明确支持盘后、周末和网络未刷新阶段。`ScreenFragment` 把这张表直接传给 `ObservationEligibility.sections`；后者的 `forDisplay` 调用 `applyQuoteGate`。新的 `isLimitUpDeferred` 只要获得任意 `Quote` 就依据其价格判断当前是否封板，`applyQuoteGate` 随后对非封板结果将 `limitUpBlocked` 和 `limitUpShrinkAcceleration` 置为 `false`，没有验证 `quote.quoteDate == TimeUtils.todayText()`。

因此，恢复的上一交易日非封板报价会临时把封板或缩量候选从第四档改为普通观察，且同代码的路线选择会把这个已解除的路线当作可选路线。只有当日新鲜报价才可以证明已开板并解除风险标记。非当日缓存应继续按持久化风险状态分组，并将缓存日期暴露为“待当日行情确认”，不能参与开板恢复判断。

## 同日复评的排序退化为代码顺序

**confirmed，中风险。** `ObservationDisplayRankingPolicy` 在复评轮次之后先比较 `lastEvaluatedDate`，它只保存到交易日；随后比较 `entryConfirmedAtMs`。`ObservationPool.evaluate` 为每一轮都接收 `evaluatedAtMs`，却只把它用于入场确认的时间，不保存普通候选最近一次成功复评的时间。`withStageResult` 也只在状态改变时追加带时间的历史记录，因此同一状态内的普通候选没有可用的最近复评时刻。

当两个候选同日、同结构、相对强度、风险、技术快照和复评轮次都相同时，排序器跳过所谓的“最近复评时间”，最终按代码决定前后。这与规则文件的“连续复评轮次、最近复评时间”不一致，也会使同日刚完成复评和早盘数据看起来同等新鲜。应在候选上持久化 `lastEvaluatedAtMs`，每次接受复评结果时更新它，并用它替代或补充日期排序。

## 核心展示契约仍没有可执行的测试保护

**confirmed，中风险。** `ObservationEligibilityTest` 已覆盖结构比资格 `score` 优先，并新增了 `BLOCKED` BUY 转第四档的断言。但它没有直接调用 `ObservationDisplayRankingPolicy` 来验证相对强度、市场风险、技术快照、复评轮次和板块平手裁决的完整优先级，也没有构造缺少市场风险的旧记录。`ScreenListUiTest` 只检查 `ScreenFragment.kt` 是否出现指定字符串，不能证明运行时传入的数据会被分组或排序正确。

补充一个小型排序矩阵即可固定契约：每个相邻优先级各用一对候选断言；再覆盖板块只能在前序字段全等时改变顺序。缓存测试应分别验证旧 `marketRisk` 缺失、旧报价不能解除封板/缩量、以及同日复评时间的顺序。这样可防止后续重新引入综合分、板块升档或旧缓存越权。

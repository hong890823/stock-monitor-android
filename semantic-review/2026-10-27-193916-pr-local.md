# Candidate-pool status grouping and display ranking

The change replaces the former board-led observation-pool presentation with four state-led groups: BUY, NEAR, OBSERVING, then deferred/risk. Its intended ordering is explicit and does not turn `ObservationCandidate.score` into a technical or composite score: structure, relative strength, market risk, technical snapshot, and re-evaluation progress precede the board tie-break. However, the UI calls the candidate-only ranking API with UI rows, so the project cannot compile. The diff also changes the observation state machine and buy-alert behavior, contrary to the requested display-only scope. **Watch for:** **confirmed** build break at the new ranking call, **confirmed** risk-marked BUY records can remain in the BUY group, and **confirmed** state/notification behavior changes are bundled with the display refactor.

**Verdict**: NEEDS_CHANGES

## High-level view

The state-group order in `ScreenFragment` is now visible as BUY, NEAR, OBSERVING, and deferred/risk. The candidate comparator encodes the requested evidence order and leaves board strength for a final tie-break, while the row copy labels a missing technical snapshot instead of deriving one from the qualification score.

The integration crosses the model/UI boundary incorrectly. `ObservationDisplayRankingPolicy` ranks `ObservationCandidate` instances, but `ScreenFragment` supplies `SelectionRowData`; the supplied lambdas also access UI-only fields through a candidate parameter.

The deferred/risk gate is applied to NEAR and OBSERVING sections but not to BUY. This makes the advertised fourth-tier risk rule asymmetric if persisted or externally produced candidates retain a BUY stage alongside risk evidence.

Separate edits alter eligibility, demotion/elimination, confirmation rounds, alert eligibility, and alert text. These changes affect the status machine and notifications rather than displaying their existing output.

## UI rows cannot use the candidate-only comparator

**Confirmed.** `ObservationDisplayRankingPolicy.rank` accepts `List<ObservationCandidate>` and its `tierOf` callback receives an `ObservationCandidate`. The new candidate branch in `ScreenFragment.addExpandableSelectionSection` instead passes `items`, which is `List<SelectionRowData>`, then reads `it.observationCandidate` inside that callback:

```kotlin
ObservationDisplayRankingPolicy.rank(
    candidates = items,
    tierOf = { ObservationEligibility.displayTier(requireNotNull(it.observationCandidate)) },
)
```

Neither the list argument nor the callback parameter has the declared API type, so Kotlin compilation stops before the new grouping UI can ship. The existing comparator can remain the source of truth by ranking the embedded candidates and applying that candidate order to rows, or it can be generalized with evidence extractors for both domain candidates and display rows.

## Deferred/risk routing excludes only NEAR and OBSERVING

**Confirmed.** `prioritizedSections` creates `buy` directly from `ObservationSection.BUY`, whereas it partitions `near` and `observing` through `isRiskOrDeferredObservation`. A candidate with `stage == BUY_CANDIDATE` and `breakoutRisk.risk == true`, `limitUpBlocked`, `limitUpShrinkAcceleration`, or a risk/defer reason therefore stays in the visible BUY group even though `displayTier` assigns the same record tier 3 and the comment says risk/deferred records must enter the fourth tier.

This is also a compatibility path: JSON persists the stage and risk fields independently, so older or externally written pool data can contain such a combination. Partition `buy` as well and append its risk subset to `deferredRisk`; this keeps the grouping invariant independent of how the record was produced.

## ObservationPool behavior extends beyond presentation

**Confirmed.** The `ObservationPool` diff changes operational behavior rather than merely adding display evidence. Weak days now accrue only when `settlesWeakDay` is set, prior BUY candidates no longer follow the former three-weak-day or ten-day-unconfirmed elimination path, daily-base and second-wave paths can satisfy eligibility, and high-board daily-base entries bypass the normal multi-round leader confirmation. The modified stage branches also preserve previously confirmed records through some gates that previously returned OBSERVING.

They violate the requested constraint that the state machine remain unchanged and alter trading behavior behind a display refactor. Split or revert the state-machine edits before landing the ranking work.

## Daily-base candidates now change buy-alert delivery

**Confirmed.** `ObservationBuyAlert.shouldNotify` newly treats `dailyBaseEntryConfirmed` as an alternative to the normal confirmation-round requirement. A daily-base candidate can therefore generate a buy alert where the previous gate would reject it. The notification body also now embeds the full candidate reason before the execution guard.

The user requirement explicitly preserves notifications. These edits affect both alert eligibility and user-visible message content, so they need to be reverted from this change or isolated and reviewed as an intentional notification change.

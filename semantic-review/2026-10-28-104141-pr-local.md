# Observation-pool grouping and limit-band filtering

The observation-pool UI now separates candidates into actionable, deferred, and risk-oriented groups while applying 10cm, 20cm, and 30cm filters by a stock's market band. Scan-result lists retain the separate current-limit-up filter. The new observation detail row refers to a value that is never declared, so the app cannot compile. The grouping also leaves ordinary `OBSERVING` candidates out of every rendered group while still counting them in the pool's route total. Watch for: **confirmed** compile failure at `ScreenFragment.kt:795` and **confirmed** loss of visible ordinary-observation candidates with inconsistent totals at `ScreenFragment.kt:632-655` and `861-895`.

**Verdict**: NEEDS_CHANGES

## High-level view

The two filter paths intentionally differ. Observation-pool rows are classified by the stock's 10cm, 20cm, or 30cm trading regime, so a candidate remains visible without being at its limit price; scan-result rows require the stock to be in the current limit-up list. This matches `LimitUpFilterPolicy.matchesMarketBand` and `matches` respectively.

`ObservationEligibility.prioritizedSections` produces an ordinary `observing` group in addition to buy, near-entry, deferred, and risk groups. The fragment only filters and renders the other five groups. Those omitted rows still contribute to `active.size` in the visible route summary.

## Undeclared limit-observation text blocks the build

**Severity: blocker. Confidence: confirmed.** `ScreenFragment.kt:795` inserts a nullable `UiKit.DetailRow` through `limitFlow?.let { ... }`, then `filterNotNull()` constructs the final non-null detail list. Kotlin can infer that list shape, but `limitFlow` itself is unresolved: no local, member, import, or project declaration exists. The generic list construction therefore never reaches type checking as intended, and the reviewed source does not compile.

The row appears intended to describe the current limit-up record for the candidate. Define `val limitFlow = rankingContext.limitByCode[item.code]?.let(LimitReport::fundFlowLine)` alongside `currentFlow`, using the existing fully-qualified name if no import is added, or delete the optional row if that information should not appear in the observation card. Either preserves the existing `filterNotNull()` behavior without inventing an empty observation.

## Ordinary OBSERVING candidates disappear from the pool

**Severity: high. Confidence: confirmed.** `ObservationEligibility.prioritizedSections` retains non-risk, non-deferred `OBSERVING` candidates in `observing` (`ObservationEligibility.kt:200-207`). `ScreenFragment.kt:632-639` rebuilds the prioritized value with market-band filtering for `buy`, `priorityReentry`, `near`, `temporarilyDeferred`, and `risk`, but does not include `observing`. The fragment then binds only those five properties at `640-644` and draws only those groups at `861-895`.

A valid candidate in `ObservationStage.OBSERVING` consequently has no row under any filter, including “全部”. This conflicts with the pool copy that describes a continuing observation pool and makes the candidate impossible to inspect, even though its strategy is included in the “策略路线” total derived from `active` at `674-675`. Add a sixth filtered `observing` property, bind it to `observingItems`, render a status group such as “👀 其他观察对象”, and include its count in the overview. The 10cm/20cm/30cm filter must be applied to that group using the same `filterObservationBandItems` path, otherwise the group would leak candidates from other bands.

## Status totals omit a live category

**Severity: medium. Confidence: confirmed.** The status overview at `ScreenFragment.kt:653-655` reports buy, near-entry, deferred, and risk counts but no ordinary-observing count. Separately, the detail sheet says `${active.size}只` in its route summary at `674-675`; `active` is built from every `ObservationEligibility.sections` value at `614-621`, which includes the ordinary-observing section. As a result, a reviewer cannot reconcile the displayed pool route total with the visible status groups whenever such candidates exist.

The same `observingItems.size` used for the missing group should be added to the overview. This gives the count, ranking scope, and visible rows the same population.

## Unused observation-rendering remnants

**Severity: low. Confidence: confirmed.** `nearEntry` is assigned `nearItems.size` at `ScreenFragment.kt:645` but is never used; the overview reads `nearItems.size` directly. `filterLimitUpItems` at `ScreenFragment.kt:509-517` is a generic version of the currently used row filter but has no call sites. These do not change runtime behavior, but retaining them makes it less clear which filtering API governs the lists. Remove both unless an imminent caller is intentionally pending.
